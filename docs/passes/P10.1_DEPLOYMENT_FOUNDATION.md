# P10.1 deployment foundation

P10.1 stores one optional `pathcode.p10.deployments.v1` section in the canonical Build record. P8 remains product source authority; P9 remains configuration and secret binding authority. P10 stores deployment target mappings, attempts, release transitions, the last PATH-established production release pointer, and separate serving observations. No P10.1 code executes Vercel commands or reads `.env.local`.

## Source and configuration identity

Preparation accepts only `buildId`, reads `authoritativeSha` from the current Build, checks its exact Git tree, rejects tracked sensitive paths and symlinks, and materializes its tracked blobs under the PATH runtime root. It verifies every blob hash and the resulting file set. Git checkout hooks and filters are not run. A dirty creator checkout is not an input. The snapshot must be cleaned after use. The source must be rechecked at the future provider submission gate.

The whole ordinary-config digest is SHA-256 over JSON of sorted `[variableName, value]` pairs. It identifies a P9 snapshot; it is not a value store or provider equality proof. Deployment records store the digest and sorted names, never duplicate config values. Secret variable values and `.env.local` are never read for deployment.

## Provider contract and recovery

Config projection plans only P9 `kind=config` entries. Command construction uses direct `vercel` spawn semantics with `--visibility config`; the value is a separate stdin payload and never argv. P10.1 constructs commands but never runs them. Provider metadata, deployment receipts, and serving observations have strict value-free fixture parsers; any unexpected field causes bounded failure.

The Build operation is persisted before any future config write. Receipts are recorded per sorted variable name. Partial projection cannot enter submission. A submission with no durable provider receipt is `uncertain`, never automatically resubmitted. Startup classification only reports recovery needs; no provider call occurs. Provider observations never move the current release pointer or create release history. Only a future explicit verified PATH switch may do that.

P10.2 remains gated on installed-CLI proof of Config visibility, stdin for add/update, value-free metadata, safe deployment receipt/status, and operation metadata lookup. Production serving inspection remains a separate proof gate. No live operation is enabled by this foundation.

## Production scale review gate

Deployment and release history are append-preserving in the Build record for bounded V1 use. Before unbounded production use, review record size, write latency, and crash recovery cost. P10.1 performs no silent trimming or compaction.
