# P10.2A preview CLI mechanical proof (no live provider action)

Installed local CLI: `/opt/homebrew/bin/vercel`, version `59.10.0`. This pass
inspected local CLI help and installed JavaScript only. It did not query an
account or project, change Config, or submit a deployment.

## Installed command facts

* `env add NAME preview --type config --yes --project PROJECT` and
  `env update NAME preview --type config --yes --project PROJECT` accept value
  from stdin. Installed `commands/env/index.js` reads stdin for both. The CLI
  treats empty stdin as no value and strips a sole final newline; PATH's command
  builder rejects inputs those semantics would alter. The CLI may also reject
  Config under a team policy requiring Sensitive variables. PATH must stop if
  that policy applies; it cannot change the P9 Config type to Secret.
* `env ls preview --json --project PROJECT` emits `envs` with key, type,
  visibility, target and optional readable Config value. The provider adapter
  discards Config values. Sensitive/Secret entries with a readable value fail
  closed. Branch-scoped entries and contradictory type/visibility fail closed.
  `configurationId` is not proof of integration origin. Only installed
  `type=system` gives a factual system classification; all other extra Config
  origin is unknown and blocks drift preflight.
* `whoami --json` and `project list --json --filter PROJECT --limit 100` are
  read-only readiness contracts. The project parser requires exactly one
  matching project and complete pagination. No creator auth/project was queried
  here, so their factual readiness remains unverified.
* `deploy --target preview --project PROJECT --meta
  pathOperationId=OPERATION_ID --json --no-wait --yes` is the intended Preview
  submission. Explicit target avoids the installed CLI's first-deployment
  implicit-production behavior. CLI `ensureLink` receives the exact project
  with `failIfNotFound`; future invocation must use only the PATH-owned source
  workspace as cwd. Any `.vercel/project.json` it creates stays there.
* `inspect DEPLOYMENT_ID --json` emits known-deployment status. It does not
  request logs. `list PROJECT --environment preview --meta
  pathOperationId=OPERATION_ID --json --limit 100` filters by metadata. PATH
  requires an exact unique match and complete pagination, with no retry from
  zero matches. Installed `list` sends metadata as `meta-` query parameters.
  The immediate deploy receipt can omit target/state; the adapter preserves
  those as unknown until a separate inspect result proves Preview and status.

## Adapter boundary

Vercel runs by direct `spawn` with `shell:false`. The child gets a narrow
execution/session environment: `PATH`, `HOME`, `TMPDIR`, `TMP`, `TEMP`, `USER`,
`LOGNAME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`,
`XDG_DATA_HOME`, `TERM`, `SYSTEMROOT`, and forced `NO_COLOR=1` when present.
`VERCEL_TOKEN`, PATH engine credentials, GitHub tokens and product values are
not forwarded. The creator's CLI login may be read through `HOME`. Raw stdout
and stderr have a one MiB bound, are never returned, and are reduced by fixed
allowlisted parsers. Failures use bounded codes. A mock spawn test proves Config
value travels in stdin alone. This executor is a P10.2A contract, not wired to
coordinator live mutations.

Raw Config listing values are ignored, never compared with P9, hashed or
persisted. P9 remains the only PATH ordinary-Config authority; future
deployment must project its exact snapshot. Extra unknown-origin Config,
missing Config, wrong type, branch scope and duplicate metadata remain
deployment blockers. Secret bindings never enter Config projection.
